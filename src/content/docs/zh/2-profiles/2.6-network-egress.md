# 校园网出口与 Clash / TUN 配置指南

开着 Clash、TUN 或其他 VPN 后，校园网登录页打不开、一直无法认证，或者 DNS 改成 `1.1.1.1` 后登录页消失，可以按本文配置。目标是让**校园网认证、联网检测和学校 DNS 走校园网，其余流量继续按原代理策略访问**。

> [!NOTE]
> 本文的软件“校园网出口”统一设置属于开发版功能，是否可用请以实际安装版本的界面为准；没有这个入口的已发布版本，可先按下文配置 Clash / Mihomo 的直连规则与 DNS。本文不代表相关开发功能已经发布。

## 先选适合自己的方案

| 当前情况 | 从哪里开始 |
| --- | --- |
| 只开系统代理，没有 TUN | 在认证喵选择“直连”，再核对学校 DNS |
| 需要长期启用 TUN，软件已有网卡选择入口 | 优先选择“指定校园网网卡（IPv4）”，设置学校 DNS，再验证 |
| 软件没有网卡选择入口，或者绑定后仍被 VPN 阻断 | 保留 TUN，使用 Clash 规则模式，为认证和检测目标配置直连 |
| 目前是“全局模式”，希望大部分流量仍然走代理 | 使用规则模式，将校园网目标放前面直连，保留最后的 `MATCH` 指向原代理组 |
| 必须保留真正的全局模式 | 阅读后面的“必须保留全局模式怎么办”，单靠普通 `DIRECT` 规则不够 |

配置前先备份当前订阅的覆写 / 合并设置。下面的 YAML 都是**需要合并的片段**，不是完整订阅；不要拿它们覆盖节点、代理组和整份 DNS 配置。

## 为什么开代理后进不了登录页

这里有三件事需要分别检查：

| 环节 | 常见故障 | 对应处理 |
| --- | --- | --- |
| 连接出口 | 认证服务器只能从校园网访问，请求却发往代理节点或其他网卡 | 选择校园网出口，或将目标设为直连 |
| 域名解析 | 校内认证域名在公网 DNS 上没有记录，或者未认证时访问不了公网 DNS | 使用学校 DNS，必要时按域名分流 |
| 联网判断 | 探测网站经过代理返回正常结果，软件误以为校园网已经认证 | 认证流量与检测流量使用相同校园网出口 |

**“绕过系统代理”和“绕过 TUN”不是一回事。** 系统代理是应用层设置，TUN 还会影响系统路由和 DNS 流量。因此，选了直连后仍受 TUN 影响，并不一定是直连开关没有生效。仅关闭代理软件的窗口，也不代表系统代理、后台服务或 TUN 已停止。

## 第一步：确认认证地址、物理网卡和学校 DNS

### 记录需要用到的地址

先从学校网络中心的文档、网络详情或已经正常工作的设备中确认：

| 信息 | 本文示例 | 如何使用 |
| --- | --- | --- |
| 认证域名 | `auth.example.edu` | 域名直连与 DNS 分流；只填主机名 |
| 认证服务器 IPv4 | `10.0.0.1` | IP 直连；一个地址使用 `/32` |
| 学校 DNS IPv4 | `10.0.0.53` | 查询校内域名，需要从校园网可达 |
| 校园网物理网卡 | “以太网”或学校 Wi-Fi 对应的接口 | 在认证喵中选择，避开 TUN / VPN 虚拟接口 |
| 已有代理组名称 | `你的代理组` | 仅用于示例最后的 `MATCH`，须替换成现有名称 |

这些值都是示例，不是任何学校的通用配置。学校 DNS 不一定等于网关，也不一定是认证服务器；不能直接猜一个 `10.x.x.x` 地址填入。

### Windows 查看网络信息

在系统网络详情中查看校园网以太网 / Wi-Fi 的 IPv4 和 DNS。也可以在 PowerShell 执行以下只读命令：

```powershell
Get-NetIPConfiguration
Get-DnsClientServerAddress -AddressFamily IPv4
```

`ipconfig /all` 也能查看同类信息。请根据接口名称、当前 IPv4 和实际连接的校园网识别物理网卡，不要把 Clash、Wintun、TAP、虚拟机接口当作校园网接口。

如果以前手动设置了 `1.1.1.1`，命令只会显示当前配置，不会告诉你学校原本下发的 DNS。此时应向学校查询，或在方便时将校园网物理网卡的 DNS 恢复为自动获取后再查看。TUN 也可能改写当前 DNS，请结合关闭 TUN 后的结果对照。

### 对比域名解析

将示例换成真实值，比较默认解析和指定学校 DNS 的解析：

```powershell
nslookup auth.example.edu
nslookup auth.example.edu 10.0.0.53
```

如果默认解析失败、指定学校 DNS 能得到合理地址，优先处理 DNS 分流。若两者都失败，还需确认学校 DNS 地址、校园网接入状态以及认证域名是否正确。

开着 TUN 时，发往指定 DNS 的请求仍可能被劫持；这组命令用于对照排查，不能单独证明查询已经从物理网卡直出。也不要把“能解析出地址”当成已经认证成功。

## 第二步：在认证喵中选择校园网出口

进入 **方案 → 认证设置 → 校园网出口**。每个方案保存自己的出口设置；多个校区或不同网络可以分别配置。

### 四种模式怎么选

| 模式 | 实际作用 | 适用情况 |
| --- | --- | --- |
| 直连（绕过系统代理） | 浏览器和 HTTP 登录忽略系统代理，连接仍受系统路由影响 | 没有 TUN，或代理侧已经为校园网配置好直连 |
| 指定校园网网卡（IPv4） | 校园网连接和程序自身的 DNS 查询绑定所选物理网卡 | 长期开 TUN、多网卡并存，希望明确指定校园网出口 |
| 指定 HTTP / SOCKS5 代理 | 经指定代理访问校园网 | 代理本身确实能够到达校园网，并且需要由它转发 |
| 系统默认（允许系统代理） | 浏览器和 HTTP 使用系统代理策略，原生 TCP 按系统路由连接 | 明确需要沿用系统代理的环境；不适合作为绕过代理的办法 |

统一出口用于浏览器 / HTTP 登录、重定向检测、网络探测和登录后验证。**软件更新、环境安装与任务仓库下载不由这项设置控制。** 自定义脚本自行管理网络连接，不能使用程序的强制网卡绑定；需要统一绑定时请选择浏览器或 HTTP 登录。

### 长期开 TUN 的设置顺序

1. 选择“指定校园网网卡（IPv4）”。
2. 选择实际接入校园网的以太网或 Wi-Fi，核对旁边的 IPv4。
3. Windows 会读取所选网卡配置的 IPv4 DNS；如果读到的是 `1.1.1.1` 或其他不适用的公网 DNS，在“学校 DNS”里填入真实学校 DNS。
4. 学校 DNS 每行一个，最多四个；通常只填 IPv4 即可，也支持 `IPv4:端口`。Linux / macOS 当前需要手动填写学校 DNS。
5. 保存方案，再执行手动认证和网络检测。编辑器中的重定向检测可以使用当前出口草稿，正式登录与常规探测使用已保存设置。

网卡刷新只更新可用清单，不会自动替你换网卡。所选网卡断开、绑定失败或学校 DNS 不可用时，程序应明确报错，不会静默切换到其他网卡或系统 DNS。更换网络、重新连接 Wi-Fi 或 DHCP 地址变化后，重新检查当前网卡信息。

> [!IMPORTANT]
> 指定网卡不会修改系统 DNS 或路由，也不保证穿过所有 VPN 防火墙。若某个 VPN 的严格路由 / DNS 拦截仍阻断连接，继续配置下面的代理规则，或临时暂停 TUN 做对照测试。不要反复更换账号密码来处理出口故障。

### 如果选择“指定代理”

只填写代理客户端实际监听的地址，例如 `http://127.0.0.1:7890`；这里不是校园网登录页。支持 HTTP、`socks5://` 和 `socks5h://`；`socks5h` 在原生请求中将目标域名交给代理解析，浏览器端的域名处理和 SOCKS5 认证支持还取决于引擎。

远程代理节点通常不能访问你所在学校的内网。即使填的是本机 Clash 地址，仍需要让 Clash 把校园网目标分到 `DIRECT`，不能因为代理端口能连接就认定能认证。

## 第三步：Clash 保留 TUN，改用规则模式

规则模式可以做到“校园网例外直连，其他流量仍按代理策略走”，不需要为了校园网长期关闭整个代理。Mihomo 的 `rule`、`global`、`direct` 是不同运行模式；真正的 `global` 使用 GLOBAL 策略，普通 `rules` 不能提供这里的校园网例外。参见 [Mihomo 运行模式说明](https://wiki.metacubex.one/config/general/#运行模式)。

### 在哪里添加规则

在客户端为当前订阅提供的**覆写、合并配置或前置规则**中添加。不同客户端的入口名称、数组合并方式可能不同，务必查看应用后的运行配置：

- 自定义校园网规则应在已有广泛匹配规则之前。
- 保留原节点和代理组，保留仍然需要的原规则。
- 下方的 `MATCH` 只是兜底示意；原配置已有 `MATCH` 时修改原条目即可，不要重复添加。
- 订阅更新后再确认自定义规则仍然存在，不要只修改会被下次订阅覆盖的生成文件。

### 需要直连哪些目标

至少检查四类：认证域名及服务器 IP、门户跳转后的其他校内域名、学校 DNS、软件实际使用的触发与检测目标。

```yaml
mode: rule
rules:
  # 先替换为本校真实地址
  - DOMAIN,auth.example.edu,DIRECT
  - IP-CIDR,10.0.0.1/32,DIRECT,no-resolve
  - IP-CIDR,10.0.0.53/32,DIRECT,no-resolve

  # 认证喵默认触发 / HTTP / URL 检测所用域名
  - DOMAIN,www.msftconnecttest.com,DIRECT
  - DOMAIN,connect.rom.miui.com,DIRECT
  - DOMAIN,connectivitycheck.platform.hicloud.com,DIRECT
  - DOMAIN,wifi.vivo.com.cn,DIRECT
  - DOMAIN,captive.apple.com,DIRECT
  - DOMAIN,detectportal.firefox.com,DIRECT

  # 保留其他原有规则；只保留一个最终 MATCH
  - MATCH,你的代理组
```

域名项不包含 `http://`、端口、路径或查询参数。`/32` 只匹配一个 IPv4；`no-resolve` 表示这条 IP 规则不主动触发域名解析，并不是“所有请求都不解析”。规则顺序和语法以 [Mihomo 路由规则](https://wiki.metacubex.one/config/rules/) 为准。

上述检测列表对应软件内置目标。改过触发地址、HTTP / URL / TCP 检测目标时，以当前方案和 **设置 → 检测** 为准补充规则，尤其不要漏掉 TCP 的 IP 目标。只让认证页直连、却让探测经代理，仍可能得到错误的联网判断。

如果学校确实使用多个子域名，可以按已确认的域名范围增加 `DOMAIN-SUFFIX`。不要为省事将整个 `edu.cn`、所有私网网段或整个浏览器进程全部直连，这会扩大规则影响范围，也不一定解决学校 DNS 的问题。

## 第四步：让校内域名使用学校 DNS

`DIRECT` 解决的是连接往哪里走，**不能替代正确的域名解析**。学校内部域名可能在公网 DNS 中不存在，或者未认证时只能访问学校 DNS；其他域名仍可保留原来的公网 DNS 配置。

### 为实际认证域名配置 DNS 分流

把以下字段合并到已有 `dns` 中，保留原来的 `nameserver`、节点域名解析及其他策略：

```yaml
dns:
  nameserver-policy:
    # 替换认证域名和学校 DNS；引号内的 #DIRECT 是 DNS 出站指定
    'auth.example.edu': 'udp://10.0.0.53:53#DIRECT'
```

这里显式指定学校 DNS 查询使用 `DIRECT`，不只依赖普通 IP 规则；Mihomo 的 DNS 连接是否遵循普通规则还受原 DNS 配置影响。此片段使用 Mihomo 语法，较旧的 Clash 内核不一定支持，应用前请检查客户端内核和配置校验结果。[DNS 分流与出站参数说明](https://wiki.metacubex.one/config/dns/#nameserver-policy)。

如果原配置已经设置了非空的 `direct-nameserver`，还需确认直连解析遵循上述域名策略：

```yaml
dns:
  direct-nameserver-follow-policy: true
```

这是对现有配置的补充，不需要为了本教程额外新增 `direct-nameserver`。相关行为见 [Mihomo 直连域名解析配置](https://wiki.metacubex.one/config/dns/#direct-nameserver-follow-policy)。

未认证时，公网 DNS 也可能无法解析明文触发和检测域名。如果表现为“认证域名可解析，但触发网址解析失败”，可以将**实际失败的触发 / 检测域名**也加入学校 DNS 策略，例如：

```yaml
dns:
  nameserver-policy:
    'www.msftconnecttest.com': 'udp://10.0.0.53:53#DIRECT'
```

它应与前面的策略合并，不能用第二份 `nameserver-policy` 把认证域名条目覆盖掉。学校 DNS 必须确实能够解析这些目标，不能仅凭 IP 端口可达判定正常。

### 使用 Fake-IP 时排除认证目标

Fake-IP 模式会向应用返回映射地址。门户依赖真实解析结果或跳转参数时，可让认证和触发域名返回真实 IP。

下面仅适用于原配置已经采用 **blacklist** 过滤模式的情况，将条目追加到原列表，不要删除其他过滤项：

```yaml
dns:
  fake-ip-filter-mode: blacklist
  fake-ip-filter:
    - 'auth.example.edu'
    - 'www.msftconnecttest.com'
    - 'connect.rom.miui.com'
    - 'connectivitycheck.platform.hicloud.com'
    - 'wifi.vivo.com.cn'
    - 'captive.apple.com'
    - 'detectportal.firefox.com'
```

如果原配置使用 `whitelist` 或 `rule`，不能直接复制上述模式，否则可能改变所有域名的解析行为；应按原模式让这些目标返回真实 IP。使用 `redir-host` 时无需添加 Fake-IP 过滤。过滤模式及匹配细节见 [Mihomo Fake-IP 配置](https://wiki.metacubex.one/config/dns/#fake-ip-filter-mode)。

### 浏览器安全 DNS 也要一起核对

手动在浏览器启用的安全 DNS / DoH 可能绕过预期的学校 DNS 路径。如果系统命令能解析、浏览器却持续报找不到服务器，可以暂时让浏览器使用系统解析做对照。具体入口随浏览器版本变化，以当前设置为准；确认问题后按实际需要恢复。

不要直接把登录 URL 中的域名替换成 IP。门户可能依赖 Host、HTTPS 证书、跨域流程或一次性跳转参数；把域名改成 IP 可能让“DNS 错误”变成新的登录错误。

## 必须保留全局模式怎么办

在真正的全局模式里继续添加普通 `DIRECT` 规则，不能达到规则模式下的分流效果。若客户端内核支持，可以在 TUN 自动路由中排除实际认证服务器、学校 DNS 等目标 IP：

```yaml
tun:
  # 仅在原有 auto-route 已启用时适用；与原列表合并
  route-exclude-address:
    - 10.0.0.1/32
    - 10.0.0.53/32
```

这只是对 TUN 路由的 IP 排除，不会自动解决系统代理、DNS 劫持、浏览器 DoH 或其他检测目标的出口问题。软件仍需使用直连 / 指定网卡，目标 IP 变化时要重新核对，检测地址也不能遗漏。不要把它当成通用的“全局模式绕过域名”开关。[Mihomo TUN 路由排除说明](https://wiki.metacubex.one/config/inbound/tun/#route-exclude-address)。

如果学校 DNS 查询仍被阻断，检查客户端的 DNS 劫持和严格路由设置。Windows 的严格路由可能增加 DNS 相关防火墙限制；先临时暂停 TUN 比较，不要直接长期关闭所有防护或批量修改系统路由。细节参见 [Mihomo 严格路由说明](https://wiki.metacubex.one/config/inbound/tun/#strict-route)。

如果你的目的只是“其余网站默认走代理”，前面的规则模式加最后一条 `MATCH` 通常更容易维护。

## 第五步：确认配置真正生效

按顺序测试，每一步只判断它负责的环节：

| 测试 | 预期结果 | 不能据此推断 |
| --- | --- | --- |
| 指定学校 DNS 查询认证域名 | 得到正确且可达的地址 | 不能证明已经认证 |
| 打开 HTTP 触发地址，或运行重定向检测 | 未认证时能到达门户，或识别出需要认证 | 不能证明账号密码正确 |
| 手动认证 | 登录任务能够完整执行 | 不能仅凭页面提示就确认网络已恢复 |
| 登录后 HTTP / URL 探测 | 从同一校园网出口得到预期状态或内容 | 不能用其他网卡或代理节点的联网状态代替 |
| 退出校园网登录后恢复检测 | 能识别未认证状态并重新执行认证 | 不应依赖浏览器已有登录 Cookie 掩盖问题 |

使用 Clash 分流时，在连接记录中查看认证、触发和检测目标是否命中预期的 `DIRECT` 规则。使用认证喵指定网卡时，流量可能直接从所选接口发出、不出现在 Clash 列表中；“没有记录”本身不等于失败，必要时结合抓包确认源 IP 和学校 DNS 目标。

测试自动恢复前，确认软件已启动检测、未处于暂停时段，且方案已保存。第一次手动测试失败时先看具体错误，不要连续点击制造多个登录窗口。

### 暂时没有真实校园网环境

可以检查配置能否保存、网卡能否枚举，以及软件在断开 / 不存在的出口配置下能否明确报错。开发测试还可以用本地 mock DNS 与门户，验证 DNS、请求来源地址和“登录 → 网络验证”是否使用同一出口。

但普通网络中打开触发地址后没有出现校园网登录页是正常现象；也不能把本地 mock 通过当作某个学校或某个 VPN 已验收通过。

## 按错误现象排查

| 现象或日志 | 优先检查 | 下一步 |
| --- | --- | --- |
| `ERR_PROXY_CONNECTION_FAILED` | 系统代理指向已停止的客户端，或代理无法访问校园网 | 核对方案出口、代理监听端口和校园网 `DIRECT` 规则；TUN 要单独检查 |
| `ERR_NAME_NOT_RESOLVED`、域名不存在 | 学校 DNS、域名策略、浏览器安全 DNS | 对比默认解析与指定学校 DNS，确认不是继续查询 `1.1.1.1` |
| 返回 `198.18.x.x` 等映射地址 | 是否处于 Fake-IP 模式 | 检查认证 / 触发域名的过滤规则，不把映射地址写成固定认证服务器 |
| 报所选网卡不可用 | 保存的接口已断开、更换或无有效 IPv4 | 连接校园网后刷新网卡，重新选择并保存，不应自动换成其他出口 |
| 选了网卡仍无法查询学校 DNS | DNS 地址错误、VPN 严格路由 / 劫持、接口权限 | 暂停 TUN 做对照；确认学校 DNS 确实从该接口可达 |
| 登录页能开，但软件提示已经联网 | 检测目标经代理或其他出口返回正常结果 | 让认证和所有启用的检测目标使用同一校园网出口 |
| 检测直连，但浏览器仍走代理 | 软件使用的渠道 / 方案不一致，或旧版独立开关配置不一致 | 新版在方案统一设置；旧版分别核对浏览器、重定向检测和网络检测配置 |
| 认证后又跳回登录页 | 登录任务、账号、运营商或门户返回值 | 进入任务调试；出口配置不能修复选择器或账号错误 |
| 订阅更新后再次失败 | 修改没有通过覆写保留，或数组被替换 | 检查实际运行配置和最终规则顺序 |
| 暂停 TUN 后立即恢复 | 问题与代理路由或 DNS 拦截有关 | 针对认证 / 检测 / 学校 DNS 做例外，不必长期停用全部代理 |

## 常见问题

### DNS 必须全部改回学校 DNS 吗

不一定。认证喵指定网卡模式可以单独设置学校 DNS；Clash / Mihomo 可以按域名选择学校 DNS，其他域名继续使用原配置。前提是学校 DNS 本身能从校园网访问。

### 已经添加认证域名直连，为什么还失败

还要检查认证服务器 IP、后续跳转域名、学校 DNS，以及软件的触发和检测目标。另需确认确实运行在规则模式，自定义项没有被更靠前的规则拦截。

### 给 campus-auth.exe 添加进程直连够不够

不一定。浏览器是独立进程，DNS 请求也可能由代理内核或系统发起，不能只靠主程序的进程名覆盖所有路径。优先核对实际域名、IP 和 DNS 的规则；也不建议把整个 Edge / Chrome 的全部浏览流量都改为直连。

### 为什么网卡绑定不自动回退到其他网络

认证必须发生在指定校园网出口上。自动回退到已联网的其他网卡或代理，可能误报成功、把账号发送到错误网络，或者让校园网一直没有真正认证。明确报错更便于定位断开的接口。

### 多方案需要重复配置吗

不同校园网、校区或运营商的网卡与 DNS 可能不同，应在各自方案里保存。只改软件设置并不会自动修改 Clash 订阅；只改 Clash 规则，也不会自动替你选中认证喵的方案。

## 仍有问题时提供哪些信息

提供代理客户端名称和内核版本、运行模式、TUN 是否开启、认证喵版本、方案出口模式、所选网卡名称，以及相关错误的时间点。日志和取证包的使用方法见 [调试与取证](../3-tasks/3.6-debug.md)。

反馈前去掉代理订阅链接、节点凭据、校园网密码、Cookie 和门户 URL 中的一次性 token；只需要域名或 IP 时，不要贴完整登录查询参数。与任务执行有关的问题也可查看 [无法自动登录](../7-faq/7.1-login.md)。
