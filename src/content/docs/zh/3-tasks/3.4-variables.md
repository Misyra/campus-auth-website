# 变量与成功判定

任务中使用 `{{变量名}}` 作为占位符，运行时会被真实值替换。因此任务文件本身无需写入账号密码，同一份任务也可被不同配置方案复用。

## 支持变量的字段

`{{VARIABLE_NAME}}` 可嵌入以下字段的字符串中：`selector`、`value`、`frame`、`option_selector`、`target_selector`、`path`、`pattern`，以及脚本内容与扩展字段。

> [!TIP]
> 控制台编辑器中，包含 `{{…}}` 的字段在保存时会高亮，便于核对变量名是否拼写正确。

## 系统内置变量

以下四个变量由当前配置方案自动注入，**无需也不应在任务中写入真实值**：

| 变量 | 来源 | 含义 |
| --- | --- | --- |
| `{{USERNAME}}` | 配置方案的 `username` | 登录账号 |
| `{{PASSWORD}}` | 配置方案的 `password` | 登录密码（运行时解密后注入，不落入任务文件） |
| `{{ISP}}` | 配置方案的 `isp` | 运营商关键字，供 `select` / `click_select` 步骤匹配 |
| `{{LOGIN_URL}}` | 配置方案的 `auth_url` 或 `trigger_url` | 直连模式下取 `auth_url`；重定向模式下取 `trigger_url`，由浏览器跟随 302 跳转至真实门户 |

## 自定义变量

在任务顶层的 `variables` 中定义，后续步骤即可引用：

```json
{
  "variables": { "campus": "south" },
  "steps": [
    { "type": "goto", "url": "https://auth.example.edu.cn/{{campus}}/login" }
  ]
}
```

## 变量优先级（由低到高）

同名变量在多处出现时，按以下顺序覆盖：

1. 任务 `variables` 中定义的自定义变量（最低）；
2. 系统内置变量 `USERNAME` / `PASSWORD` / `ISP` / `LOGIN_URL`；
3. 前序步骤通过 `store_as` 产生的运行时结果（最高）。

因此自定义变量无法覆盖真实凭据；而某一步通过 `store_as` 得到的值，可在后续步骤中覆盖同名占位符。

`store_as` 保留原始类型，插入字符串时的序列化规则为：`null` → `""`，布尔值保持 `true` / `false`，对象与数组使用 `JSON.stringify` 转换。

## success_condition：判定登录成功

```json
{ "success_condition": "login_success" }
```

执行器会查找同名 `store_as` 变量的结果做真值判断。以下值一律判定为**失败**：`false`、`null`、`0`、`""`、`"false"`、`"0"`、`"no"`、`"off"`（大小写不敏感）。

- 不填写 `success_condition` 时不做额外判定，仅检查所有 `required` 步骤是否通过。
- 典型用法是使用一个 `eval` 步骤检查页面特征，并将结果存入变量：

```json
{ "id": "check", "type": "eval", "script": "() => document.body.innerText.includes('登录成功')", "store_as": "login_success" }
```

> [!WARNING]
> 字段名为单数形式的 `success_condition`。部分社区共享任务使用了复数写法 `success_conditions`，导入后需改为单数形式，否则成功判定不生效。

## 常见技巧

| 需求 | 做法 |
| --- | --- |
| 取不到 `store_as` 的值 | 确认前序步骤确实填写了该字段且拼写一致；若该步骤 `required` 为 `false` 且被跳过，则不会产生结果 |
| 将识别出的验证码拼入后续 URL | `goto` 的 `url` 写为 `https://...?captcha={{captcha_text}}` |
| 数学验证码（如 `3+5=?`） | `ocr`（存为 `captcha_expr`）→ `eval` 计算 `{{captcha_expr}}`（存为 `captcha_answer`）→ `input` 填写 `{{captcha_answer}}` |
