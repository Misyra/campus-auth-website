# 断网自动重连

自动重连的前提是「程序知道自身已掉线」。Campus-Auth 使用**三种网络探针 + 登录前检测**共同判断网络状态，并据此决定是否自动登录。

> [!IMPORTANT]
> **至少开启三种网络探针中的一种，自动登录才会被触发**；三者全部关闭时，只能通过仪表盘「登录」按钮或接口手动触发。

各参数的默认值、取值范围与 `settings.json` 字段见 [settings.json 配置参考](../6-reference/6.1-settings.md)。

## 配置位置

**设置 → 网络监测**（`/settings/monitor`）分为三块：

| 区域 | 配置内容 |
| --- | --- |
| 左侧 · 网络状态检测 | TCP / HTTP 204 / URL 标题三种探针的开关与目标 |
| 右侧 · 登录前检测 | 网卡连接检查、认证地址可达检查、监测不走代理 |
| 顶部 · 检测与重试 | 检测间隔、超时、最大重试、重试间隔、登录后延迟、暂停时段 |

## 三种网络探针

| 探针 | 开关字段 | 默认 | 目标字段 | 判定方式 |
| --- | --- | --- | --- | --- |
| TCP 连通 | `tcp_enabled` | 关 | `tcp_targets`（逗号分隔，缺省端口按 53） | 任一目标可连通即判定为在线 |
| HTTP 204 | `http_enabled` | **开** | `http_targets`（`generate_204` 端点） | 返回 `204` 为在线，返回 `200` 为被门户劫持；必须使用明文 `http` |
| URL 标题 | `url_enabled` | 关 | `url_targets`（每行 `地址\|关键字`）与映射表 | 页面标题包含关键字即在线，否则判定为被劫持 |

> [!NOTE]
> 默认仅开启 HTTP 204 探针的原因：`generate_204` 语义干净（非 204 即被劫持）、主流厂商均提供该端点，且开销低、误判率小。TCP 与 URL 探针按需开启即可。

### 三种网络状态

对外仅暴露三种状态（枚举 `NetworkStatus`），日志与 WebSocket 推送使用英文值：

| 状态 | 枚举值 | 含义 |
| --- | --- | --- |
| 在线 | `Online` | 任一已启用探针判定网络可达 |
| 被门户劫持 | `CaptivePortal` | 204 探针返回 200，或 URL 探针未匹配到关键字；**该判定优先于离线** |
| 离线 | `Offline` | 所有探针失败，且认证地址也不可达 |

### 默认探测目标

| 探针 | 默认目标 |
| --- | --- |
| TCP | `8.8.8.8:53`、`114.114.114.114:53`、`www.baidu.com:443` |
| HTTP 204 | 小米、华为、vivo 的 `generate_204` 端点 |
| URL 标题 | Apple / Firefox / Microsoft 的联网检测页及对应关键字 |

### 如何选择探针

| 场景 | 建议 |
| --- | --- |
| 绝大多数校园网 | 保持默认，仅开启 HTTP 204 探针 |
| 希望在线判定更灵敏 | 额外开启 TCP 探针（开销最小） |
| 门户标题稳定、可作为特征 | 开启 URL 标题探针，按 `地址\|关键字` 配置 |
| 频繁误判 | 检查 204 目标是否被填成普通网页——普通网页恒返回 200，会被误判为「被劫持」而反复登录 |

### HTTP 204 探针为何必须使用明文 http

`generate_204` 依靠状态码做二值判断：204 为在线、200 为被劫持。若写成 `https`，在真正被劫持时 TLS 握手会直接失败，程序只能得到「网络错误」而非「被劫持」信号；只有明文 `http` 才能取得 200 作为劫持证据。

## 登录前检测

| 开关 | 字段 | 默认 | 作用 |
| --- | --- | --- | --- |
| 网卡连接检查 | `local_check_enabled` | 开 | 物理网卡全部断开时直接判定离线，跳过外网探测与登录 |
| 认证地址可达检查 | 认证地址预检 | — | 登录前确认 `auth_url` 可达，不可达则跳过本次；劫持型网络自动跳过 |
| 监测不走代理 | `disable_proxy` | 开（直连） | 开启时探测流量直连、不跟随系统代理；关闭则跟随系统代理（修改后需重启生效）。仅影响网络检测，不影响更新与仓库下载 |

## 探测节奏与失败冷却

两个容易混淆的机制：

- **检测间隔是自适应的，而非固定值。** `check_interval`（默认 300 秒）只是上限：在线时从 30 秒起指数放大（30 → 60 → 120…）直到封顶；一旦判定为被劫持或离线，立即收敛为固定 30 秒。因此掉线后约半分钟内即可感知并重连，无需等待一个完整周期。
- **连续失败会进入冷却。** 同一会话连续登录失败 3 次后，暂停自动登录 300 秒，避免账号被门户临时封禁。若出现「已检测到掉线却不再重试」，多半处于冷却期——等待冷却结束或手动登录一次即可恢复，无需重启。

需要立即验证当前状态时，可使用控制台「立即检测」（后台执行，30 秒超时），无需等待下一轮。

## 与重定向模式的配合

- 劫持型网络（`trigger_url` 非空）自动跳过认证地址预检。
- `{{LOGIN_URL}}` 同步为触发地址，浏览器首次导航跟随 302 跳转至真实门户。
- URL 探针的「被劫持」判定同样优先于离线。

## 故障排查

- **完全不触发登录**：确认至少开启了一种网络探针（默认仅 204 开启，被误关后不会自动触发）；确认暂停时段未覆盖当前时间。
- **频繁误判为劫持**：检查 204 目标是否被设为普通网页（恒返回 200）；核对 URL 探针关键字是否与真实页面标题一致。
