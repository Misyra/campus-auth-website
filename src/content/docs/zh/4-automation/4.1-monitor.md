# 断网自动重连

自动重连的前提是「程序知道自身已掉线」。Campus-Auth 使用**三种网络探针 + 登录前检测**共同判断网络状态，并据此决定是否自动登录。

> [!IMPORTANT]
> 自动登录依赖**强证据**：即 HTTP 204 或 URL 内容探针至少一种处于开启状态，且能给出「在线 / 被劫持」的明确结论。**TCP 单独开启不能触发明确的在线判定**，只能作为弱证据；三者全部关闭时状态为 `Unknown`，程序不会自动恢复，只能通过仪表盘「登录」按钮或接口手动触发。

各参数的默认值、取值范围与 `settings.json` 字段见 [settings.json 配置参考](../6-reference/6.1-settings.md)。

## 配置位置

**设置 → 检测**（网络检测，`/settings/monitor`）分为三块：

![网络检测设置：探针开关、重试策略与诊断辅助](/screenshots/docs/06-settings-detection.avif)

| 区域 | 配置内容 |
| --- | --- |
| 左侧 · 网络状态检测 | TCP / HTTP 204 / URL 内容三种探针的开关与目标 |
| 右侧 · 登录前检测 | 网卡连接检查、认证地址预检、登录严格模式、监测不走代理 |
| 顶部 · 检测与重试 | 检测间隔、超时、最大重试、重试间隔、登录后延迟、暂停时段 |

## 三种网络探针

| 探针 | 开关字段 | 默认 | 目标字段 | 判定方式 |
| --- | --- | --- | --- | --- |
| TCP 连通 | `tcp_enabled` | 关 | `tcp_targets`（逗号分隔，缺省端口按 53） | 任一目标可连通即 TCP 通过，但仅作弱证据，不能单独判定在线 |
| HTTP 204 | `http_enabled` | **开** | `http_targets`（`generate_204` 端点） | 返回 `204` 为在线，返回 `200` 或 `301–308` 为被门户劫持；必须使用明文 `http` |
| URL 内容 | `url_enabled` | 关 | `url_targets`（每行 `地址\|关键字`）与映射表 | 正文匹配逻辑：`3xx` 判劫持；`200` 且匹配关键字在线、不匹配判劫持、未配置关键字在线；请求/读取错误判失败 |

> [!NOTE]
> 默认仅开启 HTTP 204 探针的原因：`generate_204` 语义干净（非 204 即被劫持）、主流厂商均提供该端点，且开销低、误判率小。TCP 与 URL 探针按需开启即可。

### 三种网络状态

对外仅暴露三种状态（枚举 `NetworkStatus`），日志与 WebSocket 推送使用英文值：

| 状态 | 枚举值 | 含义 |
| --- | --- | --- |
| 在线 | `Online` | HTTP 204 或 URL 内容探针给出「在线（Pass）」判定 |
| 被门户劫持 | `CaptivePortal` | HTTP 204 返回 `200`/`301–308`，或 URL 探针得到劫持结论；**该判定优先于离线** |
| 离线 | `Offline` | 所有已启用探针均判定失败 |

### 默认探测目标

| 探针 | 默认目标 |
| --- | --- |
| TCP | `8.8.8.8:53`、`114.114.114.114:53`、`www.baidu.com:443` |
| HTTP 204 | 小米、华为、vivo 的 `generate_204` 端点 |
| URL 内容 | Apple / Firefox / Microsoft 的联网检测页及对应关键字 |

### 如何选择探针

| 场景 | 建议 |
| --- | --- |
| 绝大多数校园网 | 保持默认，仅开启 HTTP 204 探针 |
| 希望在线判定更灵敏 | 额外开启 TCP 探针（开销最小，仅作弱证据） |
| 门户返回正文稳定、可作为特征 | 开启 URL 内容探针，按 `地址\|关键字` 配置 |
| 频繁误判 | 检查 204 目标是否被填成普通网页——普通网页恒返回 200，会被误判为「被劫持」而反复登录 |

### HTTP 204 探针为何必须使用明文 http

`generate_204` 依靠状态码做二值判断：204 为在线、200 为被劫持。若写成 `https`，在真正被劫持时 TLS 握手会直接失败，程序只能得到「网络错误」而非「被劫持」信号；只有明文 `http` 才能取得 200 作为劫持证据。

## 登录前检测

| 开关 | 字段 | 默认 | 作用 |
| --- | --- | --- | --- |
| 网卡连接检查 | `local_check_enabled` | 关 | 主要用于手动「网络测试」时的本地链路诊断；自动监测只在关闭「登录严格模式」时额外采集一次本地链路证据。开启与否不影响登录能否进行 |
| 认证地址预检 | `check_auth_url` | 关 | 仅在**手动登录 / 单次登录**前对 `auth_url` 做一次可达性预检；自动监测不走该预检，劫持型网络也跳过 |
| 登录严格模式 | `strict_login_mode` | 开 | 仅在探测给出明确门户结论时才自动登录；关闭后退化为「网卡已连接且未确认在线也尝试登录」的宽松触发 |
| 监测不走代理 | `disable_proxy` | 开（直连） | 开启时探测流量直连、不跟随系统代理；关闭则跟随系统代理（保存后下一轮检测生效）。仅影响网络检测，不影响更新与仓库下载 |

## 探测节奏与失败冷却

两个容易混淆的机制：

- **检测间隔是自适应的，而非固定值。** `check_interval`（默认 120 秒）只是上限：在线时从 30 秒起指数放大（30 → 60 → 120…）直到封顶；一旦判定为被劫持或离线，立即收敛为固定 30 秒。因此掉线后约半分钟内即可开始重连，无需等待一个完整周期。
- **连续失败会进入冷却。** 同一会话连续登录失败 3 次后，暂停自动登录 300 秒，避免账号被门户临时封禁。若出现「已检测到掉线却不再重试」，多半处于冷却期——等待冷却结束或手动登录一次即可恢复，无需重启。

需要立即验证当前状态时，可使用控制台「网络测试」（后台执行，30 秒超时），无需等待下一轮。新安装默认 `startup_action=none`（启动后不自动开始检测），需在仪表盘右上角点击 **启动检测** 开始；希望启动即自动守护时，在 设置 → 系统 把「启动后执行」改为「进入监测」，或用 `--startup-action monitor` 覆盖。另注意：暂停时段不仅静默周期监测，也会拦下手动点「启动检测」后的立即探测——暂停时段内点了没反应属预期，手动登录不受影响。

## 与重定向登录的配合

- 劫持型网络（触发地址非空，或认证地址留空）自动跳过认证地址预检。
- `{{LOGIN_URL}}` 同步为触发地址，浏览器首次导航跟随 302 跳转至真实门户。
- URL 探针的「被劫持」判定同样优先于离线。

## 故障排查

- **完全不触发登录**：确认 HTTP 204 或 URL 内容探针至少一种开启（默认仅 204 开启，被误关后不会自动触发）；TCP 单独开启不足以给出明确在线判定，三者全关时也不会自动恢复。同时确认暂停时段未覆盖当前时间。
- **频繁误判为劫持**：检查 204 目标是否被设为普通网页（恒返回 200）；核对 URL 探针关键字是否与真实返回正文一致。
