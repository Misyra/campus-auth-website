# 网络检测原理

本篇讲清 Campus-Auth 如何判断当前网络处于什么状态、三种探针在**单独或同时启用**时分别如何裁决，以及自动登录在什么条件下才会触发。它是 [断网自动重连](4.1-monitor.md) 的底层机制：只想知道开关怎么配，看前者；想理解误判、漏判与多探针并用规则，读这一篇。

## 快速选择（普通用户看这里）

不确定怎么配时照做即可，三个探针可以同时开、互不冲突：

1. **默认只开「HTTP 204」就够了。** 它出厂已开启，适合绝大多数校园网，平时不用改。
2. **只有当 204 判断不准时，再按需叠加其他探针：**
   - 能上网却反复弹登录、或想让在线判断更快更稳 → 加开「TCP 连通」（开销最小，作辅助）；
   - 学校登录页内容固定、能拿一句话当特征 → 加开「URL 内容」并配关键字。
3. **同时开多个时怎么下结论（记住这两句）：**
   - 只要 204 或 URL **任意一个发现「被门户拦截」，就判定需要登录**（哪怕另一个显示正常）；
   - 只要 204 或 URL **任意一个确认在线、且没有谁报拦截，就判定在线**（此时 TCP 失败也不影响）。
   - **TCP 不能单独用来判定在线**：只开 TCP 时即使端口能连通，状态也是「未知」，必须配合 204 或 URL。

> [!WARNING]
> 若「能上网却一直反复登录」，先检查 HTTP 204 的地址是不是被填成了普通网页——普通网页永远返回 200，会被一直误判成「被劫持」。204 探针只能填 `generate_204` 类专用探测地址。

## 总览：结论是怎么一步步得出的

校园网属于 **Captive Portal（强制认证门户）**：设备已连上接入设备、拿到内网 IP，但在浏览器认证前，对外访问会被网关「丢弃 / 302 跳转 / 200 替换成登录页」。所以「网卡连着」不等于「能上公网」，需要主动探测。

整个判定是一个**自下而上的四层漏斗**，理解它就理解了全部：

| 层级 | 做什么 | 产出 |
| --- | --- | --- |
| ① 单个目标 | 对每个探测地址发一次请求 / 连接 | 五种单目标结果之一 |
| ② 类内汇总 | 同一类探针配了多个目标时，收敛成该类的一个结果 | TCP / HTTP / URL 各一个结果 |
| ③ 跨类裁决 | 把三类结果按**固定优先级短路**，得到基础网络状态 | 在线 / 被劫持 / 离线 / 未知 |
| ④ 认证入口修正 | 非在线时再探一次校内认证地址，修正状态与动作 | 最终状态 + 恢复建议 |

> [!IMPORTANT]
> 多个探针同时启用时，**不是投票、不是取平均，而是按固定优先级「命中即定」**。下文「多个探针同时启用时如何裁决」一节会用真值表逐条讲透，那是本篇的核心。

### 单目标的五种结果

第 ① 层，每个探测地址只会得到以下结果之一，后续所有汇总都基于它：

| 结果 | 含义 |
| --- | --- |
| 通过 `Pass` | 连通成立（TCP 连上 / 收到 204 / 内容匹配关键字） |
| 劫持 `Captive` | 拿到门户拦截证据（200 替换页、3xx 跳转、内容不符） |
| 证据不足 `Inconclusive` | 链路通但收到 1xx/4xx/5xx 等非预期状态码，分不清是「目标服务器故障」还是「网关拦截」 |
| 失败 `Fail` | 超时、连接被拒、DNS 失败、读正文中途中断等物理不通 |
| 未启用 `Disabled` | 该探针没开或目标列表为空（裁决时直接忽略） |

### 最终的四种网络状态

第 ③④ 层对外只暴露四种状态（枚举 `NetworkStatus`，日志与 WebSocket 推送使用英文值）：

| 状态 | 枚举值 | 含义 | 默认动作 |
| --- | --- | --- | --- |
| 在线 | `Online` | 公网正常可用 | 不动作 |
| 被门户劫持 | `CaptivePortal` | 连进校园网但待认证 | 尝试自动登录 |
| 离线 | `Offline` | 物理断网或探针全失败 | 等待网络恢复 |
| 未知 | `Unknown` | 没开探针，或证据不足 | 继续观察、谨慎处理 |

> [!IMPORTANT]
> 「没有测量」绝不伪装成「确认离线」：三个探针全部关闭时状态是「未知」而非「离线」，且不会触发任何自动登录，避免毫无依据地反复登录。

## 三种探针分别怎么判断

### TCP 连通探针——只看「端口通不通」的弱探针

对目标 `host:port` 做一次最朴素的 **TCP 三次握手**，不发送任何 HTTP 数据，能连上就算这个目标通过。

- **目标格式**：严格的 `host:port`，必须显式带端口；IPv6 写成 `[::1]:53` 方括号形式，裸 `::1` 会因冒号歧义被拒绝。
- **多目标收敛方式：竞速（Race）**。所有目标同时发起，**第一个连上就立即判定本类通过**，不再等慢速目标（整体耗时≈最快的一次连接），剩余连接只给 50ms 收集已快速失败的明细；**只有全部目标都连不上才判失败**。
- **它只可能产出「通过 / 失败」**，不会产出「劫持」或「证据不足」——因为它根本不发 HTTP，无从识别门户。
- **证据强度：弱。** 端口能连不代表能上公网：门户网关常放通 DNS（53）和常用端口，TCP 通但网页仍被劫持；反过来 TCP 连不上也可能只是目标 IP 被校园网策略屏蔽。因此它只能当辅助，不能单独定在线。

### HTTP 204 探针——看状态码的主力强探针（默认开启）

向专门的 **`generate_204` 探测端点**发 GET。这类端点正常时一定返回空的 `204`；未认证时网关劫持请求，返回 200 登录页或 3xx 跳转。于是**状态码直接对应结果**：

| 收到的状态码 | 单目标结果 | 解释 |
| --- | --- | --- |
| `204` | 通过 | 请求直达官方服务器，公网正常 |
| `200` | 劫持 | 本应 204 却回 200，是网关替换的登录页 |
| `301`~`308` | 劫持 | 被重定向到认证门户 |
| 1xx / 4xx / 5xx | 证据不足 | 状态码非预期，不强行定性 |
| 请求直接报错 | 失败 | 超时 / 拒连 / DNS 失败 |

它**只读状态码、不读正文**，并被设置为**绝不自动跟随重定向**——「存在一次 3xx」本身就是要抓的劫持证据。

> [!NOTE]
> 为什么必须用明文 `http://` 而非 `https://`：HTTPS 被劫持时 TLS 握手直接失败，只能得到「网络错误」；只有明文 HTTP 才能拿到 200/302 作为劫持证据。默认目标全部是 `http://`。

### URL 内容探针——读正文比对关键字的强探针

有些检测端点（Apple / Firefox / 微软联网检测页）正常时返回 **200 + 一段固定文本**，无法用 204 语义判断。URL 探针在收到 200 后**读取正文、检查是否包含预期关键字**（子串匹配）：

| 现象 | 单目标结果 |
| --- | --- |
| `3xx` 重定向 | 劫持（被带去登录页） |
| `200` 且正文含关键字 | 通过（内容正确，确认真在线） |
| `200` 但正文不含关键字 | 劫持（200 是被替换的登录页） |
| `200` 但该地址没配关键字 | 通过（无预期即不校验内容） |
| 1xx / 4xx / 5xx | 证据不足 |
| 请求报错 / 读正文中途中断 | 失败 |

正文采用**流式读取、最多 64KB**，达到即停，不为比对短关键字下载整页；读取中途连接中断一律判失败，即使半截正文恰好含关键字也不误报。它能识别「状态码也是 200、但页面被掉包」这种更隐蔽的劫持。

### 类内多目标如何收敛

HTTP 204 与 URL 探针配多个目标时**并发请求、等全部返回后汇总**，汇总优先级固定为：

```text
劫持  >  通过  >  证据不足  >  失败
```

即**任一目标被劫持，本类就判劫持**，哪怕另一个目标返回了通过——这是为了防止网关「只劫持部分域名」时漏判。TCP 不走此规则，它用前面说的竞速。

### 三种探针一览

| 维度 | TCP 连通 | HTTP 204 | URL 内容 |
| --- | --- | --- | --- |
| 工作层级 | 传输层（握手） | 应用层（状态码） | 应用层（状态码 + 正文） |
| 判断依据 | 端口能否连上 | 204 / 200 / 3xx | 3xx / 200 内容是否匹配 |
| 是否读正文 | 否 | 否 | 是（限 64KB） |
| 多目标收敛 | 竞速：首个连上即通过 | 劫持 &gt; 通过 &gt; 证据不足 &gt; 失败 | 同 HTTP 204 |
| 可能的结果 | 通过 / 失败 | 五种齐全 | 五种齐全 |
| 证据强度 | 弱（不能单独定在线） | 强 | 强 |
| 默认开关 | 关 | **开（唯一默认开启）** | 关 |
| 默认单目标超时 | 2s | 10s | 10s |

## 多个探针同时启用时如何裁决

这是理解一切组合行为的关键。拿到第 ② 层的三个结果（TCP、HTTP、URL 各一个）后，裁决器**先剔除「未启用」项，再自上而下逐条匹配，命中第一条就定结论**，后面不再看：

1. **一个探针都没启用** → `未知`（原因：未启用探针），不自动恢复；
2. **HTTP 204 或 URL 任一为「劫持」** → `被门户劫持`（高置信），建议登录；
3. **HTTP 204 或 URL 任一为「通过」** → `在线`（高置信），不动作；
4. **所有已启用探针全部「失败」** → `离线`（中置信），等待网络恢复；
5. **其余情况** → `未知`（低置信）：其中只要含「证据不足」就归为证据不足，否则只可能是「TCP 单独通过」的弱证据，统一等待更多证据。

### 组合结果真值表

下表全部来自程序内置的判定逻辑与其单元测试，可直接对照排查：

| TCP | HTTP 204 | URL | 最终基础状态 | 说明 |
| --- | --- | --- | --- | --- |
| 任意 | **劫持** | 任意 | 被门户劫持 | 劫持优先级最高，哪怕 TCP 通过、URL 通过也照样判劫持 |
| 任意 | **通过** | 非劫持 | 在线 | 强证据确认在线，TCP 失败也不影响 |
| 任意 | 非劫持 | **通过** | 在线 | 同上，URL 确认在线即可 |
| 通过 | 劫持 | — | 被门户劫持 | 「TCP 能连 + 204 被劫持」正是待认证的典型样子 |
| 失败 | 通过 | 未启用 | 在线 | 单个弱失败不能推翻强通过 |
| 失败 | 失败 | 失败 | 离线 | 所有启用项全失败才算离线 |
| 通过 | 失败 | 未启用 | 未知（弱证据） | 仅 TCP 通，不足以确认在线 |
| 失败 | 证据不足 | 未启用 | 未知（证据不足） | 非预期状态码，不强行定离线 |
| 通过 | 证据不足 | 未启用 | 未知（证据不足） | 证据不足优先于 TCP 的弱通过 |
| 未启用 | 劫持 | 失败 | 被门户劫持 | 「未启用」项直接忽略，不参与裁决 |
| 未启用 | 未启用 | 未启用 | 未知（无探针） | 不触发任何自动登录 |

由此得到四条直觉规则：

- **强证据压过弱证据**：在线 / 劫持只由 HTTP 204、URL 决定，TCP 只能影响「全失败才离线」这一条，无法单独定在线；
- **劫持压过在线**：规则 2 在规则 3 之前，强探针之间出现分歧时以「劫持」为准，防止选择性劫持漏判；
- **全失败才是离线**：只要还有一个探针没失败（哪怕只是证据不足或 TCP 通），就不判离线；
- **证据不足不下定论**：非预期状态码既不误判在线、也不误判离线，留给下一步认证入口去判断。

## 认证入口：最后一道修正

第 ③ 层只看公网探针；当结论不是「在线」时（仅周期自动监测会执行，手动诊断不执行），程序会再 **TCP 直连一次校内认证地址 `auth_url`**（默认 5s 超时，强制直连、不走系统代理），用「公网不通、但校内认证器通不通」来修正结论——这正是「连进校园网、待认证」的典型特征。

| 基础状态 | 认证地址结果 | 最终状态与动作 |
| --- | --- | --- |
| 在线 | 任意 | 不动作 |
| 被劫持 | 地址非法 / 缺失 | 提示修正配置，暂停自动恢复 |
| 被劫持 | 不可达 | 谨慎只登录一次 |
| 被劫持 | 可达 / 重定向模式跳过 / 未检查 | 正常尝试登录 |
| 离线 / 未知 | **可达** | 证据不足型未知 → 维持未知、谨慎登录一次；其余（含全失败离线）→ **升级为被门户劫持**，尝试登录 |
| 离线 / 未知 | 非法 / 缺失 | 提示修正配置 |
| 离线 / 未知 | 不可达 | 离线 → 等待网络；未知 → 等待更多证据 |

> [!NOTE]
> 「谨慎只登录一次」由引擎按当前配置版本去重：同一版配置只试一次，离开异常状态后清零。这是为了防止探测目标自身周期性 5xx 时，在「目标故障 + 认证服务器在线」情况下反复误登录。

### 恢复建议不等于立即登录

监测层**只产出恢复建议，不直接登录**；是否真的执行，还要通过引擎的运行门控（未暂停、配置未过期、不在冷却期、没有登录在途等）。建议共这些种：

| 建议 | 含义 |
| --- | --- |
| 不动作 | 已在线 |
| 尝试登录 | 证据充分，启动自动登录 |
| 谨慎登录一次 | 证据偏软，按配置版本只登录一次 |
| 等待网络 | 更像物理断网 |
| 等待更多证据 | 证据不足，等下一轮 |
| 修正配置 | 认证地址缺失 / 非法，需用户处理 |
| 无探针证据 | 没开有效探针，禁止自动恢复 |

## 一轮检测如何编排

三种探针由统一的监测服务并发执行，对外有三个入口，共用同一套流程、区别只在用途：

| 入口 | 用途 | 采集物理网卡 | 产出恢复建议 |
| --- | --- | --- | --- |
| 周期自动监测 | 后台定时判断 | 否 | 是（含认证入口修正） |
| 手动网络诊断 | 界面点「网络诊断」 | 是（需开关） | 否 |
| 登录后验证 | 登录后确认恢复 | 否 | 否 |

每轮顺序：**热读配置（改了下一轮即生效）→ 已启用探针并发探测（整体耗时≈最慢一路）→ 跨类裁决 → 非在线时补认证入口 → 产出报告**。HTTP 客户端为长生命周期连接池，且**默认直连、绕过系统代理、不跟随重定向**：被门户拦截时本就没有公网，系统代理此刻不可达，走代理会把「待认证」误判成「离线」；代理 / 证书设置变化时客户端会热重建，无需重启。

## 辅助检测

### 物理网卡 / 本地链路

通过系统原生命令枚举网卡、默认网关与 Wi-Fi 名（Windows 用 `ipconfig`/`route`/`netsh`，Linux 用 `ip`/`iwgetid`，macOS 用 `ifconfig`/`networksetup`），结果缓存 30 秒，并剔除回环、无 IP、媒体断开、链路本地地址及 VMware / Hyper-V / Docker / VPN 等虚拟网卡。它**仅在手动诊断时作参考展示，不参与公网裁决**；网卡信息另用于配置方案按网关 / SSID 自动匹配。

### 认证门户地址自动检测

配置界面的「自动检测认证地址」是一次性手动工具（非周期检测）：复用 204 / 内容探针语义，**手动逐跳跟随最多 5 次重定向**，把网关下发的跳转地址作为候选填回表单（需用户确认，不自动保存）。结果分为解析出门户地址、当前已在线、被劫持但无重定向地址（需手动复制）、所有目标不可达四种。

## 探测节奏：自适应间隔

程序不按固定间隔死板探测，而是按状态自适应，兼顾反应速度与资源占用：

| 情形 | 间隔策略 |
| --- | --- |
| 非在线（离线 / 被劫持） | 固定约 30 秒一轮，加密探测以便快速反应 |
| 持续在线 | 从 30 秒起按连续在线轮数指数退避，逐步拉长到配置的检测间隔，稳定在线时几乎不产生探测流量 |
| 探针全部禁用 | 沿用配置间隔，不退化成 30 秒空转 |

## 配置项与默认值

下列字段在 **设置 → 网络检测** 配置，完整定义见 [settings.json 配置参考](../6-reference/6.1-settings.md)，每轮热读、改后下一轮生效：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| 检测间隔 | 120s | 稳定在线时被指数退避动态拉长 |
| TCP / HTTP 204 / URL 开关 | 关 / **开** / 关 | 默认仅 HTTP 204 |
| 物理网卡检查 | 关（仅手动诊断） | 本地链路参考，不参与裁决 |
| 监测不走代理 | 开 | 探测流量直连 |
| TCP 默认目标 | `8.8.8.8:53`、`114.114.114.114:53`、`www.baidu.com:443` | 超时 2s |
| HTTP 204 默认目标 | 小米 / 华为 / vivo 的 `generate_204` | 超时 10s，须为 204 端点 |
| URL 默认目标 | Apple / Firefox / 微软检测页及对应关键字 | 超时 10s |
| 认证地址超时 | 5s | 认证入口 TCP 预检 |
| 登录后延迟 | 5s | 等门户生效后再验证 |
