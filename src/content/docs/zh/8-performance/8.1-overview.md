### 关键判断

1. **空闲 CPU 低于常规采样精度。** `TotalProcessorTime` 精度为 15.6 ms，多轮 90–300 s 窗口直接读数均为 0。必须用「累计 CPU 时间 ÷ 窗口时长」法才能定量，因此空闲态数值只能给出**上界**。
2. **浏览器套件是体积与内存的绝对大头**（≥1.8 GB 磁盘），Rust 侧不存在与之可比的常驻开销，量级差达**两个数量级**。
3. **排除口径与实际运行路径一致。** Worker 为懒加载 + 空闲 300 s 回收，全程实测**子进程数为 0**。
4. **发现一个真实缺陷**：`/api/history` 先读 30 天全量、后才按 `limit` 截断，成本随累积历史线性增长。这是本轮唯一有实际影响的问题，详见「观察点与建议」。
5. **Virtual Bytes 4.27 GB 不是问题**，经最小基线对照实验证伪，无需处理。

## 测量方法与口径

### 被测版本

被测二进制构建于 **2026-09-18 09:34:58**。测量完成后，工作区另有直连登录 / Profile 相关功能的改动，**已逐项核实：本页涉及的全部代码路径均未被触及**——包括 `history`、`container`、`run_loop`、`monitor`、`ws`、`tray`、`system`、`bridge`、`snapshot` 等模块，`frontend/dist` 亦未重新构建。

因此上述结论对被测二进制成立，并对当前源码继续成立。如需严格对齐最新工作区，重新执行 `cargo build --release` 后复测即可。

### 测量方法

- 每轮使用**全新隔离 `--base-path`**，不污染用户配置与实例锁。
- 通过 `--startup-action` 与配置文件补丁组合出各目标场景（监测开关、探测间隔、日志级别、暂停窗口等）。
- 进程指标取自 `Get-Process` 与 Windows 性能计数器（`Process` 类别）。
- **CPU 采用「累计 CPU 时间差分 ÷ 墙钟时长」法**，规避 `TotalProcessorTime` 的 15.6 ms 量化误差；对低于量化阈值的场景，通过**增加请求数累加**让信号高于噪声。
- 子进程经 `Win32_Process.ParentProcessId` 追踪，确认是否拉起浏览器 / Worker。

### 指标口径

| 指标 | 定义 |
| --- | --- |
| 单核百分比 | `100 × ΔCPU时间 / Δ墙钟`，1 核满载 = 100 % |
| 全机百分比 | 单核值 ÷ 16（逻辑核数） |
| 工作集（Working Set） | 含 exe/dll 可共享映像页，任务管理器「内存」列口径 |
| 私有工作集（Working Set - Private） | 仅本进程私有提交页，多开时的真实增量 |
| 24 h 折算 | 线性外推，仅用于量级感知，非长期实测 |

### 测量局限（如实声明）

- **空闲 CPU 只能给出上界**：窗口内总 CPU 低于 15.6 ms 时读数为 0，故标为 `<0.0001 %`。
- **离线场景为模拟**：以黑洞地址 `10.255.255.x` 构造超时，探测超时行为等价，但 RTT 分布与真实校园网断网不同。
- **`cargo-bloat` 未安装**，`.text` 的依赖级构成未细分。
- **未覆盖范围**见文末，请勿把本页读作「全路径已验证」。

> **一处数据修正**：本页早期版本的「API 压测 4399 req/s / 2.47 % 单核」混入了一个**不存在的端点** `/api/status`（实际返回 404）。现已在「API 与 IO 负载场景」中用全部返回 2xx 的真实端点在预检后重测并替换。

## 观察点与建议

按「实测影响」排序。非瓶颈项不作过度优化。

### /api/history 读取 30 天全量后才截断 —— 唯一实测异常点（已于 v5.0.0 修复）

> [!NOTE]
> **此问题在当前版本已修复**：`/api/history` 带 `limit` 时已改为按天倒序的「取最近 N 条」路径（`query_latest`），成本与 `limit` 相关而非历史总量相关——即下文建议的根治改法。以下实测数据基于修复前的 v5.0.0-alpha.10，保留作为分析过程与优化前基线。

这是本轮补充测试中**唯一发现的有实际影响**的问题，与其余观察项性质不同。

`history` 路由（修复前）先取 30 天**全量**记录，再按 `limit` 截断：

```rust
let from = to - Duration::days(30);
let mut history = history.query(from, to).await?;   // 全量读入 + 逐行 JSON 解析 + 排序
if let Some(limit) = params.limit { /* 此时才截断 */ }
```

前端 `historyApi.fetch(30)` 只请求 **30 条**，但服务端仍需读取并解析全部 30 天记录 —— **`limit` 对 I/O 与解析量完全没有节流作用**。

- **线性增长**：≈0.75 µs/条，随累积历史单调放大，30 天保留期内不会自行收敛。
- **对照端点**（`/api/system/info`、`/api/login/status`）单请求 CPU 均为 0.00 ms —— 差距达**三个数量级**，不是测量噪声。
- **内存无泄漏**：WS 全程稳定在 21.8 MB。问题在 CPU 与延迟，**不在内存**。
- **触发频率为用户驱动**（仪表盘挂载、手动刷新、手动登录后），非定时器轮询；叠加前端 5 s 防抖守卫，实际压力有限。但 20 000 条时单次 55 ms 延迟已可感知，且每次刷新都重复付出该成本。

**建议**（按优先级）：

1. 在 `query` 层支持「只需最近 N 条」—— 按天**倒序**枚举文件、倒序读行，凑够 `limit` 即停，使成本与 `limit` 相关而非与历史总量相关。**根治改法**。
2. 次优：`HistoryStore::query` 增加目标条数参数，让 `limit` 在读取阶段即生效。
3. 不建议只加缓存 —— 历史每日追加，缓存失效判断反而增加复杂度。

> [!IMPORTANT]
> 本轮仅做性能分析，**未改动任何源码**。是否修复请另行决策。

#### 关键对照：同为大文件读取，日志接口无此问题

日志接口只读日志文件**尾部 512 KB**，在 **265 MB** 日志下实测单请求延迟 **6.7 ms**、服务端 CPU **0.00 ms**。

这反证上述缺陷源于「先全量、后截断」的**设计取舍**，而**非文件大** —— 同样的体积，只要读尾部即可做到成本恒定。二者是同一类需求（「取最近 N 条」）的两种实现，对比鲜明。

日志导出接口受 `LOG_EXPORT_MAX_TOTAL_BYTES = 50 MB` 总量上限约束，且仅由用户手动点击触发（非定时路径），风险已受控。

### WS 状态快照每秒全量推送 —— 观测项，非瓶颈

uptime 追踪每秒触发一次状态合并，进而触发 `watch` 通知，每个 WS 连接随即克隆整个 `StatusSnapshot`（含多个 `String`）并序列化为 887 B 帧发送。

- 实测代价：4 连接 + 62 req/s 合计 **0.035 % 单核**，当前**不构成瓶颈**。
- 潜在放大点：每次克隆涉及 `String` 堆分配，连接数上升时线性增长（上限 16）。
- **建议**：连接数或快照字段继续增长时，再考虑增量编码或按 `snapshot_version` 去重推送。**当前无需改动。**

### 托盘 50 ms 轮询 —— 续航问题，非 CPU% 问题

Windows 上托盘以 `recv_timeout(50ms)` 循环，每秒 20 次唤醒。

- 实测：CPU 占比**低于测量精度**（`<0.0001 %` 单核），不构成 CPU 负担。
- **真实影响**：持续周期性唤醒会妨碍 CPU 进入深度 C-state / Modern Standby，影响笔记本续航 —— **这一点无法通过 CPU% 指标体现**，容易被性能分析忽略。
- **建议**：若在意续航，改为事件驱动（阻塞 `recv` + 状态变化时由泵任务主动唤醒）。属可选优化。

### Engine 5 秒空闲兜底唤醒 —— 观测项

引擎任务即使无任何事件也每 5 秒醒一次，用于墙钟异常兜底。

- 实测：对 CPU 无可测影响。
- **建议**：**保持现状**。该分支承担「墙钟跳变后重估」的兜底职责，删除会引入定时器失效风险，收益不成比例。

### Virtual Bytes 4.27 GB —— 非问题，无需处理

见「关于 4.27 GB Virtual Bytes」一节的对照实验。与最小 tokio 基线仅差 89 MB，属常态地址空间预留。

### 二进制 25 MB —— 权衡项，非性能问题

`.text` 17.96 MB 为主要构成。项目引入 `boa_engine`（内嵌 JS 引擎，用于直连登录的用户加密脚本）等重型纯 Rust 依赖，是与「避免 C 依赖交叉编译问题」的显式权衡。磁盘体积对常驻内存无影响（仅映射按需分页）。
